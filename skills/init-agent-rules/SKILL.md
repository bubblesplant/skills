# 增量同步项目规则

以本技能 `assets/` 的当前内容为同步源，将适用的规则差异实际写入目标项目。默认补充缺项、合并不冲突的新要求，并按下文条件更新旧模板条款；保留项目已有约定与有效布局，不将目标目录镜像成模板目录。模板自包含，不依赖模板来源仓库。

## 先确定作用范围

- 使用用户指定的目标项目；未指定时使用当前工作目录所属的项目。不要把当前目标自动扩大到外层 Git 仓库、脚手架仓库或用户主目录。
- 用户指定某个包、模板或条款时，只同步该范围及必要的入口、链接；未限定时，识别整个目标项目中适用的模板。
- 修改前读取目标路径上已有的 `AGENTS.md`，并遵循其中适用的约定。先检查已有规则，再写入文件。
- 根据工作区配置、包清单和源代码识别项目结构及子包职责。`apps`、`packages` 等目录名只是线索；不要仅凭这些名字或嵌套的 `package.json` 判定 monorepo，也不要将依赖、构建产物、测试夹具或内嵌示例当作子包。
- 读取已有 `AGENTS.md`、`.agents/rules` 及其引用关系，找出通用规则、前端规则和项目或包专属规则。其他工具的配置仅用于识别已有约定，不擅自删除或改写。
- 本次操作只同步规则文档及其入口、链接，不因新规则而创建、修改或移动业务代码，也不调整依赖、构建配置或生成类型声明。目录归组、代码拆分等条款供后续相关开发任务使用。

## 目录布局

以下是缺少规则时的默认布局。已有文件位置和适用范围清晰、入口有效时沿用，只修复本次同步涉及的链接，不为统一结构迁移已有文件。

单体项目的新增规则集中在一套入口中；单体前端应用的前端规则也放在这一套中，不为 `src`、`pages`、`components` 人为创建子包。

```text
项目根目录/
  AGENTS.md
  .agents/rules/
```

monorepo 新增的通用规则放根目录，本包专属规则放实际子包。包名和深度以目标项目为准。

```text
项目根目录/
  AGENTS.md
  .agents/rules/              # 跨包通用规则
  <实际子包路径>/
    AGENTS.md
    .agents/rules/            # 本包专属规则
```

仅为本次有适用规则需要落盘的范围补齐缺少的入口和目录，不为没有专属规则的包批量创建空入口或空目录。保留已有的深层局部规则，不强行压平或提升为全局规则。

同步根入口时，以 [AGENTS.root.md](assets/AGENTS.root.md) 的完整当前内容为来源，按本次选定范围逐项合并适用条款和按需表。模板中逐级查找并阅读 `AGENTS.md` 的条款保留原文且仅保留一份；已有更详细的读取约定保留额外约束。该条款已覆盖子目录规则发现，子包入口不再重复，也无须逐包增加重复说明。

## 内置模板与放置位置

先枚举 `assets/` 的文件清单，再结合本次范围和项目类型读取适用模板。下表是用途索引，不是文件白名单；发现表外新增模板时，根据其目录和内容确认适用条件、目标位置及入口。无法确认用途时暂不写入，交付时说明缺失信息，不静默遗漏或盲目复制。

以下规则是内置默认规则，包含前端使用的后端接口定义规范，不包含后端服务实现的专属要求。

| 用途           | 模板                                                     | 目标位置                                 |
| -------------- | -------------------------------------------------------- | ---------------------------------------- |
| 根入口         | [AGENTS.root.md](assets/AGENTS.root.md)                  | 根 `AGENTS.md`                           |
| 前端入口       | [AGENTS.frontend.md](assets/AGENTS.frontend.md)          | 前端包 `AGENTS.md`；单体前端则合入根入口 |
| 其他包入口     | [AGENTS.package.md](assets/AGENTS.package.md)            | 没有前端规则的包 `AGENTS.md`             |
| 通用代码设计   | [代码设计.md](assets/rules/common/代码设计.md)           | 根 `.agents/rules`                       |
| 共用类型与方法 | [共享代码.md](assets/rules/common/共享代码.md)           | 根 `.agents/rules`                       |
| 前端文件拆分   | [文件拆分.md](assets/rules/frontend/文件拆分.md)         | 前端作用范围的 `.agents/rules`           |
| 页面 API 归属、类型与 JSDoc | [页面接口.md](assets/rules/frontend/页面接口.md) | 前端作用范围的 `.agents/rules`           |
| 组件命名       | [组件命名.md](assets/rules/frontend/组件命名.md)         | 前端作用范围的 `.agents/rules`           |
| 弹窗封装       | [弹窗组件.md](assets/rules/frontend/弹窗组件.md)         | 前端作用范围的 `.agents/rules`           |
| React SVG 使用 | [ReactSVG使用.md](assets/rules/frontend/ReactSVG使用.md) | React Web 作用范围的 `.agents/rules`     |

- 前端应用及 UI 组件包按实际职责应用前端模板。纯 UI 库没有页面时不添加页面接口规则；纯后端或工具包不添加前端规则。
- 同步页面接口规则时，一并同步后端接口定义的 TypeScript 类型与 JSDoc 要求，并将“新增、修改后端接口定义”合入对应的按需触发条件。具体要求保留在页面接口规则文件中，`AGENTS.md` 仅配置条件及规则链接。
- React SVG 规则仅用于渲染 DOM 的 React Web 应用及 UI 组件包；Vue、React Native 和 Taro 小程序不套用。仅在匹配的作用范围内读取 `ReactSVG使用.md`，并向该范围的 `AGENTS.md` 按需表追加“新增、修改或使用 React SVG” → `[React SVG 使用](.agents/rules/ReactSVG使用.md)`，不将这一行加入通用前端入口模板。
- 项目没有代码线索时，使用用户说明的项目类型。无法判断时先同步范围内的通用规则，确有需要再询问缺失信息，不凭空创建前端包。
- 后端已有规则保留在原有适用范围；不要从其他项目带入特定实现或测试命令。

## 路径适配与文件复制

先查找目标范围内是否已有语义对应的规则，不仅检查模板同名路径。没有对应规则时，才复制适用模板并替换参数；已有对应规则时执行下一节的合并，不使用强制复制覆盖。

| 模板参数               | 如何确定                                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{{SHARED_TYPES_DIR}}` | 相对项目根的共用类型目录。优先沿用目标项目；没有约定的 JS/TS 单体项目默认 `src/types`，monorepo 默认 `packages/shared/types`。其他语言按其结构适配。                               |
| `{{SHARED_UTILS_DIR}}` | 相对项目根的公用方法目录。优先沿用目标项目；没有约定的 JS/TS 单体项目默认 `src/utils`，monorepo 默认 `packages/shared/utils`。其他语言按其结构适配。                               |
| `{{PAGE_DIR}}`         | 相对当前前端包的实际页面目录，例如 `src/pages`、`src/app`。遵循路由框架的文件约定；没有既有约定时使用 `src/pages`。                                                                |
| `{{SHARED_RULE_LINK}}` | 从最终的 `文件拆分.md` 所在目录，到根目录实际共享代码规则文件的相对链接。单体通常为 `共享代码.md`；`apps/web` 包通常为 `../../../../.agents/rules/共享代码.md`。深层包须重新计算。 |

模板中的目录是默认约定，既有项目路径和用户明确要求优先。如果目标项目已经分开组织类型或方法，修改条款描述以准确保留其组织方式。`config/index.ts`、`.tsx`、组件扩展名等示例也应匹配实际语言和框架，不因示例要求项目引入 TypeScript 或 React；页面接口规则明确要求的接口类型与 JSDoc 仍须同步。

同步 React SVG 规则时，核对目标构建工具、现有 SVG 导入方式、图标封装和目录，并适配模板。已有封装时使用其真实路径和参数；没有 `SvgIcon` 时沿用项目已支持的 SVG 渲染方式，不生成引用不存在组件的要求。Vite 和 Rsbuild 的转换插件不同，只有现有构建配置支持时才写入对应组件导入语法，不强制改用 `?react`。没有可确认的组件导入方式时仅保留可用的 URL 使用方式和通用 SVG 规范。目标存在组件使用文档时，才按规则文件的最终位置添加相对链接。

每个入口以“适用条件 → 相对规则链接”配置按需加载。条件应指出具体任务，例如修改页面 API、调整组件命名、封装弹窗，或文件达到拆分规则约定的阈值；阈值和适用条件以合并后的规则为准。不要把所有规则改成每次必读。单体前端将根入口和前端入口的条件合成一个表格；复制入口模板时去掉本次不适用的模板行，保留目标已有且有效的入口。

## 增量合并

保留目标已有的有效要求、说明、工具维护块及无关内容。按条款含义和实际作用范围比较，不能仅按标题、文件名或文本相似度认定可覆盖。

| 差异情况 | 处理方式 |
| --- | --- |
| 目标缺少适用规则或条款 | 补入适当的已有文件；无对应文件时新建，并补齐按需入口。 |
| 已有同义条款 | 复用现有内容和有效链接，不重复添加，也不只为措辞一致而改写。 |
| 同主题增加不冲突的要求 | 合入现有对应位置，保留项目补充内容及作用范围。 |
| 已接入模板的旧条款发生修改 | 只有既有同步记录或可核验的版本历史能证明目标对应条款仍与上次同步基线一致时，才用适配后的新条款替换，并同步相关入口条件。 |
| 与项目自定义冲突，或无法确认旧条款来源 | 保留目标条款，暂不写入相冲突的新要求；交付时列出源与目标的差异、未应用原因。用户本次明确指定的变更要求优先。 |
| assets 删除了文件或条款 | 不据此删除项目内容，也不删除仍有效的入口；仅在用户明确要求清理时处理。 |

没有可验证基线时，不把目标的现有条款推定为未修改的旧模板。例如模板阈值从 300 改成 400，目标仍为 300，仅凭这两个值不能判断是否应覆盖。无需为一次同步新建版本跟踪系统；可完成其余增量，并说明保留的差异。只有冲突阻碍用户明确指定的结果时，才询问该冲突点。

新增触发条件并入已有“按需规则”部分；仅合并本次涉及的重复行或同义说明，不追加另一份同名章节。已有规则文件名清晰且作用范围合适时继续使用，入口与内部链接跟随实际文件。不同包的项目约定各自保留。

完成同步后，项目没有其他修改时再次使用相同 assets 执行应无文件变化。不反复追加表格、生成副本或改动无关规则；不把执行历史、同步清单或迁移日志写进项目规则。

## 用户明确要求整理或迁移时

默认增量同步不拆分、移动、重命名或删除已有规则文件。用户明确要求整理结构时，才按实际作用范围迁移：根规则混有多个范围时，只拆出相关条款并保留其余内容，不把包专属规则提升为全局规则。

迁移前查找所有引用，迁移后更新入口和规则内部的相对链接。确认原内容完整保留、旧引用均已更新后，才移除被迁移的旧文件；仍需兼容原路径时保留原入口。

## 完成检查与交付

- 按本次范围逐项核对适用模板及条款：已新增、已合并、无需变化或因冲突保留；表外资产也已判断用途，没有遗漏适用增量。同步根入口时检查选定范围内的所有条款，不只检查规则发现条款。
- 检查本次新增或修改的规则可由其作用范围内的入口找到，条件与最终条款一致，涉及的本地链接可解析，模板参数均已替换；其他包没有被混入前端要求，已有约定和工具维护块得到保留。
- 审查最终差异，确认没有改动业务文件或进行未要求的迁移，相同输入再次执行不会产生差异。使用项目已有工具检查本次 Markdown 格式；只有文档变化时不运行无关的业务测试。
- 简短告知新增或合并了哪些入口和规则、采用的项目路径，以及未应用的冲突或用途不明的资产；没有变化时直接说明已是最新适用状态。不停留在目录结构建议。
