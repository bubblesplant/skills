# 初始化项目规则

实际创建或合并规则文件。支持单体项目和 monorepo，使用本技能内置的文件模板，不依赖模板来源仓库。

## 先确定作用范围

- 使用用户指定的目标项目；未指定时使用当前工作目录所属的项目。不要把当前目标自动扩大到外层 Git 仓库、脚手架仓库或用户主目录。
- 修改前读取目标路径上已有的 `AGENTS.md`，并遵循其中适用的约定。先检查已有规则，再写入文件。
- 根据工作区配置、包清单和源代码识别项目结构及子包职责。`apps`、`packages` 等目录名只是线索；不要仅凭这些名字或嵌套的 `package.json` 判定 monorepo，也不要将依赖、构建产物、测试夹具或内嵌示例当作子包。
- 读取已有 `AGENTS.md`、`.agents/rules` 及其引用关系，找出通用规则、前端规则和项目或包专属规则。其他工具的配置仅用于识别已有约定，不擅自删除或改写。

## 目录布局

单体项目只建立一套；单体前端应用的前端规则也放在这一套中，不为 `src`、`pages`、`components` 人为创建子包。

```text
项目根目录/
  AGENTS.md
  .agents/rules/
```

monorepo 在根目录放通用规则，在每个实际子包放本包的规则。包名和深度以目标项目为准。

```text
项目根目录/
  AGENTS.md
  .agents/rules/              # 跨包通用规则
  <实际子包路径>/
    AGENTS.md
    .agents/rules/            # 本包专属规则
```

识别出的实际子包均建立 `AGENTS.md` 和 `.agents/rules`；没有专属规则时可以保留空规则目录。单体项目原有的更深层局部规则可以保留，不因初始化而强行压平。

最外层 `AGENTS.md` 必须包含以下原文，且只保留一份：

```markdown
## 目录说明

- 修改文件前，须从文件所在目录逐级向上查找并阅读相关的 `AGENTS.md`（如存在），并遵循其中的说明。
```

该约定已覆盖子目录的规则发现，无须再逐包增加“修改某包时还须读取某包 AGENTS.md”的重复说明。子包文件也不重复这段约定。

## 内置模板与放置位置

只读取本次需要应用的模板。以下规则是内置默认规则，不包含任何后端专属规则或“回复后讲解后端知识点”的要求。

| 用途           | 模板                                                     | 目标位置                                 |
| -------------- | -------------------------------------------------------- | ---------------------------------------- |
| 根入口         | [AGENTS.root.md](assets/AGENTS.root.md)                  | 根 `AGENTS.md`                           |
| 前端入口       | [AGENTS.frontend.md](assets/AGENTS.frontend.md)          | 前端包 `AGENTS.md`；单体前端则合入根入口 |
| 其他包入口     | [AGENTS.package.md](assets/AGENTS.package.md)            | 没有前端规则的包 `AGENTS.md`             |
| 通用代码设计   | [代码设计.md](assets/rules/common/代码设计.md)           | 根 `.agents/rules`                       |
| 共用类型与方法 | [共享代码.md](assets/rules/common/共享代码.md)           | 根 `.agents/rules`                       |
| 前端文件拆分   | [文件拆分.md](assets/rules/frontend/文件拆分.md)         | 前端作用范围的 `.agents/rules`           |
| 页面 API 归属  | [页面接口.md](assets/rules/frontend/页面接口.md)         | 前端作用范围的 `.agents/rules`           |
| 组件命名       | [组件命名.md](assets/rules/frontend/组件命名.md)         | 前端作用范围的 `.agents/rules`           |
| 弹窗封装       | [弹窗组件.md](assets/rules/frontend/弹窗组件.md)         | 前端作用范围的 `.agents/rules`           |
| React SVG 使用 | [ReactSVG使用.md](assets/rules/frontend/ReactSVG使用.md) | React Web 作用范围的 `.agents/rules`     |

- 前端应用及 UI 组件包按实际职责应用前端模板。纯 UI 库没有页面时不添加页面接口规则；纯后端或工具包不添加前端规则。
- React SVG 规则仅用于渲染 DOM 的 React Web 应用及 UI 组件包；Vue、React Native 和 Taro 小程序不套用。仅在匹配的作用范围内读取 `ReactSVG使用.md`，并向该范围的 `AGENTS.md` 按需表追加“新增、修改或使用 React SVG” → `[React SVG 使用](.agents/rules/ReactSVG使用.md)`，不将这一行加入通用前端入口模板。
- 新项目没有代码线索时，使用用户说明的项目类型。无法判断时先建立通用规则，确有需要再询问缺失信息，不凭空创建前端包。
- 后端已有规则保留在原有适用范围并纳入对应入口；不要从其他项目带入 `AppException`、`GlobalExceptionFilter`、错误码目录或特定测试命令。
- 不为初始化规则创建业务代码、共享包实现或修改依赖配置；React SVG 规则初始化也不创建 `SvgIcon` 组件、不调整构建配置或生成类型声明。

## 路径适配与文件复制

目标文件不存在时，可以直接复制适用模板，再替换参数。目标文件已存在时执行下一节的合并，不使用强制复制覆盖。

| 模板参数               | 如何确定                                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{{SHARED_TYPES_DIR}}` | 相对项目根的共用类型目录。优先沿用目标项目；没有约定的 JS/TS 单体项目默认 `src/types`，monorepo 默认 `packages/shared/types`。其他语言按其结构适配。                               |
| `{{SHARED_UTILS_DIR}}` | 相对项目根的公用方法目录。优先沿用目标项目；没有约定的 JS/TS 单体项目默认 `src/utils`，monorepo 默认 `packages/shared/utils`。其他语言按其结构适配。                               |
| `{{PAGE_DIR}}`         | 相对当前前端包的实际页面目录，例如 `src/pages`、`src/app`。遵循路由框架的文件约定；没有既有约定时使用 `src/pages`。                                                                |
| `{{SHARED_RULE_LINK}}` | 从最终的 `文件拆分.md` 所在目录，到根目录实际共享代码规则文件的相对链接。单体通常为 `共享代码.md`；`apps/web` 包通常为 `../../../../.agents/rules/共享代码.md`。深层包须重新计算。 |

模板中的目录是默认约定，既有项目路径和用户明确要求优先。如果目标项目已经分开组织类型或方法，修改条款描述以准确保留其组织方式。`config/index.ts`、`.tsx`、组件扩展名等示例也应匹配实际语言和框架，不要求项目引入 TypeScript 或 React。

复制 React SVG 规则时，核对目标构建工具、现有 SVG 导入方式、`SvgIcon` 封装和图标目录，并适配规则中的默认路径与参数。Vite 和 Rsbuild 的转换插件不同；已有其他导入约定时沿用项目约定，不因初始化规则强制改用 `?react`。目标存在组件使用文档时，才按规则文件的最终位置添加相对链接；文档不存在时不生成该链接。

每个入口以“适用条件 → 相对规则链接”配置按需加载。条件应指出具体任务，例如修改页面 API、调整组件命名、封装弹窗，或文件超过 300 行；不要把所有规则改成每次必读。单体前端将根入口和前端入口的条件合成一个表格。

## 合并已有规则

1. 保留原有有效要求、说明、工具维护的标记块和无关内容。先理解含义，不能仅按标题或文件名判断重复。
2. 同义规则只保留一份；同主题的不同要求合到同一文件。已有文件名清晰且位置合适时继续使用该文件名，入口链接跟随实际文件。
3. 模板默认值与既有明确约定冲突时，保留目标项目的约定并调整模板。用户在本次任务明确要求的内容优先。已有规则之间无法判断的真实冲突，保留内容并只询问冲突点，同时完成不依赖该答案的整理。
4. 按真实适用范围归位：通用规则放根，前端规则放前端包，后端或其他包专属规则放所属包；单体项目在根规则目录按入口条件区分。不要把仅适用一个包的旧规则提升为全局规则。
5. 根规则文件混有多个范围时，只拆出需要归位的条款，保留剩余内容。不同前端包的约定可以各自不同，不强行同步。
6. 迁移前先查找所有引用，迁移后更新入口和规则内部的相对链接。确认原内容完整保留、旧引用均已更新后，才移除被迁移的旧文件；仍需兼容原路径时保留原入口。
7. 将新增触发条件并入已有“按需规则”部分，去掉重复行和重复规则发现说明，不追加另一份同名章节。已有详细的目录读取约定可保留额外约束，但与要求原文同义的部分应合并。
8. 重复调用时只补缺项、修路径和合并新增要求；不反复追加表格、生成副本文件或改动无关规则。不把执行历史、迁移日志写进项目规则。

## 完成检查与交付

- 确认单体或 monorepo 的目录布局符合实际项目，根入口含所需原文，适用的前端规则已落盘，其他包没有被混入前端要求。
- 检查每份规则能通过其作用范围内的入口条件找到，所有本地链接可解析，模板参数均已替换，迁移内容无遗漏，已有约定和工具维护块得到保留。
- 审查最终差异，验证再次执行不会重复增加内容。使用项目已有工具检查本次 Markdown 格式；只有文档变化时不运行无关的业务测试。
- 简短告知创建或合并了哪些入口和规则、采用了哪些项目路径。仅有真实冲突需要用户决定时指出它，不停留在目录结构建议。
