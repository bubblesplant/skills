# 项目 Agent 配置

将 `assets/` 中适用的个人规则写入目标项目，并与已有约定合并。`assets/` 提供规则与入口模板，本文件规定配置流程。

## 当前覆盖范围

- 前端应用与 UI 组件包：合入通用规则，并按职责、框架和配置选择前端及 React 条件规则。
- Node.js 后端与工具包：当前使用代码设计、共享代码等通用规则资产，保留项目已有的后端约定；不套用前端规则，也不凭空新增后端框架规则。
- 前后端一体项目：支持 Next.js / Nuxt 等单应用全栈、普通前后端分目录仓库及 monorepo。根目录承载通用规则，包、目录或混合代码范围按实际职责选择局部规则；前端规则不扩散到独立的服务端实现。

## 处理边界

- 使用用户指定的项目、包或目录；未指定时使用当前工作目录所属项目。不要自动扩大到外层仓库、脚手架仓库或用户主目录。
- 只修改目标范围内的 `AGENTS.md`、`.agents/rules` 及其必要链接。不要为落实规则而修改业务代码、依赖、构建配置或生成文件。
- 初始化或接入前读取覆盖目标的上级约定、目标内已有的 `AGENTS.md`、相关规则及引用文件，遵循仍然有效的项目约定和工具维护说明。读取上级约定不扩大修改范围。
- 用户本次要求初始化、接入或补齐，即完整比较当前适用的个人规则基线并语义合并；不把目标目录镜像成 `assets/`。模板后续变化不会自动回写项目，资产改名或删除也不授权迁移、删除已有规则；整理、移动、删除须有用户明确要求。

## 初始化与接入流程

1. 根据工作区配置、包清单、构建入口和源码职责确定项目根、指定范围及各规则作用域。不要仅凭目录名或嵌套 `package.json` 判定 monorepo，也不要把同包内的前后端职责视为相同。
2. 枚举 `assets/`，并完整读取 [规则选择清单](references/rule-selection.md)，按项目根及有独立职责的包、目录或代码范围选择规则与入口资产。
3. 只有存在 React 手动记忆化候选规则时，才完整读取 [React Compiler 检测](references/react-compiler-detection.md)，并对每个 React 作用范围独立判断。非 React 范围不执行该检测。
4. 沿用已有且清晰的布局，缺少时使用清单中的默认位置；按下节逐条比较合并，再替换模板参数、适配路径和重算相对链接。没有适用规则时不创建空入口或规则目录。
5. 写入后按完成检查核对入口、规则与最终差异。

## 与已有规则合并

- 选中的资产是用户个人规则基线。按作用范围、触发条件、具体要求、约束强度和例外比较语义，不按标题、文件名或文字相似度去重；不能因同主题约定跳过缺失要求，或把“必须”“禁止”改成建议。
- 目标条款已完整覆盖资产意图时，复用目标内容、文件位置和有效入口，不重复添加，也不为统一措辞而改写。
- 目标只覆盖部分意图时，将缺失要求合入最接近的现有规则文件；没有合适文件时才新增规则文件，并补齐对应的按需入口。
- 同主题但不冲突的项目细节与个人规则同时保留。路径、别名、命令、扩展名和示例按项目实际适配，但不得改变规则本身的义务。
- 规则应落在最窄且正确的作用范围内。保留根、包、目录和混合职责代码的边界，不把局部约定提升为全局规则，也不无故缩小全局个人规则的范围。
- 表面冲突先通过拆分作用范围、触发条件或明确例外化解；更具体的规则只在其明确范围内生效。
- 同一范围内确实无法兼容时，不写入两条互相矛盾的规则。用户本次已明确优先级时按其要求处理；否则暂缓该冲突条款，并在交付中并列说明资产要求、目标要求、作用范围和待决定项，不能静默忽略个人规则。
- 保留无关内容、注释、工具维护块和有效链接。

## 完成检查

- 将每项适用资产归类为“已有覆盖、已合并、已新增、条件不适用或冲突待定”，确认没有遗漏清单中的适用规则。
- 检查新增或修改的规则都能从正确作用范围的入口按需找到；本地链接及其标题片段可解析，所有模板参数已替换，入口条件与最终规则一致。
- 对每个 React 作用范围记录 Compiler 判断：已启用或无法确认时不新增手动记忆化规则及入口；确认未启用时规则与入口必须同时存在。
- 检查 React、页面、浏览器样式等规则只覆盖对应职责；单应用全栈及混合目录中的独立服务端实现不承担前端专属规则，没有适用规则的范围不生成空入口。
- 审查最终差异，确认未修改范围外内容，且相同输入再次执行不会重复追加表格、章节或规则副本。只运行与规则文档相关的格式和链接检查。
- 简短交付新增、合并或复用的规则位置，以及条件跳过项、未确认项和冲突；不要只给目录建议而不实际完成初始化或接入。
