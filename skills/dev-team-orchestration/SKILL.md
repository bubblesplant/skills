# 多角色协作编排

核心不是"按 角色 1 → 角色 2 → 角色 3 排队"，而是用 Agent 工具派生真实 subagent，靠结构化文档传递上下文，靠确认门挡住 garbage in。前端、后端可并行；测试发现的缺陷按来源回流，不一次性丢给用户。

## 触发边界

仅在"从需求到上线的完整功能开发"时使用：用户带来一个需要多个角色协作的功能需求（新功能、较大改造、前后端联动），需要拆解、定契约、并行实现、联调测试。

不要用于：小修小补、单个 bug、单个角色能搞定的改动、纯样式调整、只生成脚手架、纯视觉复刻（一比一还原已有网站）。如果用户表述模糊，例如"帮我做个功能""加个模块"，先询问是否需要按完整功能开发流程走，确认前不要启动阶段 0。

## 角色定义

全部用 Agent 工具派生真实 subagent，不靠主 agent 自己分饰多角。

- **产品(PM)**：把模糊需求结构化为 PRD（用户故事 + 验收标准 + 接口草案）。
- **契约/架构**：基于 PRD 产出 API 契约 + 数据模型，作为前后端唯一真相源。
- **前端 ‖ 后端**：基于同一份契约**并行**开发，在同一消息内派生两个 subagent。
- **集成/联调**：主控 agent 承担，合并联调、记录缺陷清单。
- **测试(QA)**：含 Playwright E2E；按 PRD 验收标准逐条验证；发现缺陷 → 回流对应角色。

## 主控职责

主 agent 不写业务代码，只做四件事：派生 subagent、汇总产物、把控确认门、分发缺陷回流。subagent 之间不直接对话，所有上下文经主控用结构化文档传递。阶段间产物写入 `artifacts/dev-team/`（`PRD.md`、`contract.md`、`test-report.md` 等），不靠口头转述。

## 阶段流程与确认门

| 阶段 | 产出 | 确认门 |
|---|---|---|
| 0 需求输入 | 澄清模糊点；询问是否对标参考站 | ✅ 停住等用户确认 |
| 1 PRD | `PRD.md`（用户故事 + 验收标准 + 接口草案） | ✅ 停住等用户确认 |
| 2 契约 | `contract.md`（端点 / 字段 / 状态码 / 数据模型） | ✅ 停住等用户确认 |
| 3 并行开发 | 前端、后端代码 | ❌ 自动跑完 |
| 4 集成联调 | 联调结果、缺陷清单 | ❌ 自动 |
| 5 测试 + 回流 | `test-report.md`；缺陷回派修复 | ❌ 循环到无严重缺陷 |

确认门话术统一为："已产出 X（路径），关键待确认项：……。请确认或补充，等你说继续我再进入下一阶段。" 列出空白项，不要默认通过。

## 绝对流程

不要跳过阶段 0、1、2 的确认门直接写代码。即使用户说"直接做""别废话开干"，也要先过 PRD 和契约——需求错一点，后面所有 subagent 全在错的基础上返工。只有用户明确确认 PRD 和契约并说"继续"，才进入并行开发。

## 单一真相源

前后端必须基于同一份 `contract.md`。任何一方发现契约缺失或矛盾，不要自创字段，必须回到契约阶段更新 `contract.md`，并由主控通知另一方同步。契约之外的"口头约定"无效。

## 并行规则

前端、后端两个 subagent 必须在同一消息内并行派生（Agent 工具单消息多调用），不要串行。派生前把 `contract.md` 路径作为共同上下文传给两边。通用技术栈不硬编码，由各 subagent 自行读取目标项目判断（`AGENTS.md`、`agents.md`、`package.json`、已有路由、组件风格、状态管理、样式写法）。

## 回流闭环

测试阶段发现缺陷，按来源分发，不要堆给用户：

```text
前端缺陷（UI/交互/页面状态）      → 前端 subagent
后端缺陷（接口/数据/逻辑）        → 后端 subagent
契约歧义（字段/状态码/边界定义）  → 回契约阶段，更新 contract.md 后再派发
```

循环修复直到无严重缺陷。每轮回流由主控指派，subagent 之间不互相直接派活。

## Playwright 双用途

**用途 A（默认）——测自研成果**
QA 在阶段 5 对我们自己产出的页面跑 E2E：默认态、空态、加载态、错误态、关键交互、接口联调路径。逐条覆盖 `PRD.md` 的验收标准，不只验默认页。

**用途 B（可选）——测参考站，仅在阶段 0 用户明确提供参考站 URL 时启用**
QA 在契约阶段前用 Playwright 打开参考站，抓关键行为、接口、状态作为契约的对标输入。**轻量侦察**：产出一份"参考站行为要点"附在 `contract.md`，供前后端对齐。只抓够用的关键行为，不做逻辑链表格、阶段化逐项侦察、最终循环截图对比那类重流程——那是一比一复刻才需要的，本 skill 用不到。

## Playwright 环境

QA 跑 E2E 前先检查当前项目/环境是否已有 Playwright 能力，能否启动浏览器截图。如果没有 Playwright、浏览器二进制缺失，或最小烟测失败，**不要继续，也不要直接安装**。先提醒用户缺少能力，并询问是准备环境，还是改用单元测试、接口测试、静态检查等替代手段。只有用户明确要求协助安装时，才给安装建议或执行命令。

## QA 阻塞协议（跑测遇到阻力必须停下问用户）

Playwright 实际跑测时，遇到以下情况 QA subagent 必须**停下询问用户**，不得自行绕过：

1. **登录墙**：目标页需登录才能到达。询问用户提供测试账号、已登录会话或手动登录后的状态。**不要求长期有效凭据，不把账号密码硬编码进代码或写入产出文档**；敏感值用运行期注入，或在记录里用 `<redacted>` 占位。
2. **二次验证 / 验证码 / 风控**（含 403、429、人机校验）：停下问用户，不尝试绕过验证码、风控或付费墙。
3. **权限态到不了**：某些状态需要特定角色权限才能触发。问用户提供该角色账号，或确认跳过并标记"无法验证"。
4. **不可逆操作**：支付、删除、真实提交、发消息、改配置等可能造成不可逆结果的操作，先停下确认再触发，不擅自执行。
5. **页面跳失 / 资源加载失败 / `networkidle` 超时**：记录现象与已做的非侵入式检查，问用户下一步。

询问时必须说明：当前现象、阻塞了哪个状态或验收项的验证、需要用户提供什么（账号、会话、截图、确认跳过等）。页面只有部分可访问时，先问是否只验证可访问部分；确认后继续，并把不可达状态标记"无法验证"。

不要要求长期有效的敏感凭据。不要绕过任何验证、风控、付费墙或权限控制。

## 凭据安全

测试需要的账号密码只在运行期使用，**不得**：硬编码进源码、写进 `contract.md`/`test-report.md` 等产出文档、长期持有、提交到版本库。记录测试结果时用 `<redacted>` 占位敏感值。

## 通用技术栈

本 skill 不绑定框架。各 subagent 进入工作前先读取目标项目的规则与栈：`AGENTS.md`、`agents.md`、`.agents/`、`package.json`、已有路由、组件目录、状态管理、样式系统、命名约定。若读不到相关规则，在产物里注明"未发现项目规则文件"，再按该项目的现有约定继续，而不是套用某套默认栈。

## 记录约定

阶段产物优先写入项目内 `artifacts/dev-team/`：`PRD.md`、`contract.md`、`integration-notes.md`、`test-report.md`，可选参考站时再加 `reference-site-notes.md`。如果项目不适合写入，用允许的临时目录并在回复里说明。最终回复必须说明：覆盖的验收标准数量、通过/失败/无法验证的项、回流轮次、剩余缺陷或"无严重缺陷"、跑过的检查/构建/测试命令。

## 质量标准

- 不跳过阶段 0/1/2 的确认门；需求未确认不写代码。
- 前后端必须基于同一份契约，契约外的约定无效。
- 前端、后端并行派生，不要串行。
- 缺陷按来源回流，循环到无严重缺陷为止。
- QA 不只测默认页，必须覆盖验收标准中的每一条。
- 遇到登录、验证码、风控、不可逆操作、到不了目标页，停下问用户，不自行绕过。
- 不硬编码、不长期持有、不写入产出文档任何账号密码。
