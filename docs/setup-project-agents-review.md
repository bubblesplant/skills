## 1. 结论与定位

你的理解是对的。这个 skill 应当负责：**根据项目真实架构，初始化或补齐项目的 `AGENTS.md`，并接入适用的个人开发规则。**

| 项目现状 | 应有行为 |
| --- | --- |
| 没有 `AGENTS.md` | 识别项目结构，生成必要的项目说明、目录职责、实际命令、工作边界和规则入口。 |
| 已有 `AGENTS.md` | 保留有效内容，补齐缺失信息和适用规则，修复已确认失效的路径与入口，避免重复。 |
| 有多层 `AGENTS.md` | 尊重现有作用范围，把内容放在正确层级。 |
| 规则确实冲突 | 保留可兼容内容；无法判断优先级的条款单独列出，不写入互相矛盾的要求。 |

现有实现已经比较完善地处理了“个人规则接入与语义合并”。主要差距是：**还没有明确要求把识别到的项目架构，转化为最终 `AGENTS.md` 中可用的项目上下文。** 此外，前后端一体项目的覆盖不应只依赖 monorepo 和真实子包。

建议做一次范围明确的优化：补齐这两项能力，修复一处清单遗漏，再精简重复说明。无需推翻现有目录和规则体系。

## 2. 当前实现中应保留的设计

- **语义合并。** 已有规则完整覆盖时复用，部分覆盖时补缺，不因标题或文件名不同重复生成。
- **个人规则基线。** 按适用范围完整保留，不能擅自把“必须”“禁止”改成建议。
- **按需读取。** `AGENTS.md` 提供入口，详细规则放在 `.agents/rules/`，避免每次加载全部规则。
- **作用范围隔离。** 根规则、前端规则、React 条件规则分别选择，避免扩散到无关包。
- **修改边界。** 初始化规则文档不授权修改业务代码、依赖或构建配置。
- **可重复执行。** 再次运行不应增加重复章节、表格行或规则副本。

当前整个 skill 只有 21 个文件、约 306 行，`SKILL.md` 本身约 52 行。问题主要在能力定义和信息分工，不在文件数量；不建议为了精简而合并所有规则文件。

## 3. 发现的问题

### 3.1 核心缺口：识别了架构，但没有明确要求输出架构信息

依据：[SKILL.md](../skills/setup-project-agents/SKILL.md) 第 26—31 行、[根入口模板](../skills/setup-project-agents/assets/AGENTS.root.md) 全文。

当前流程会识别根目录、包职责和框架，但主要用于选择规则资产。根入口模板只有“目录说明”和“按需规则”；其中“目录说明”实际是查找指令文件和组织业务文件的要求，没有项目自身的目录职责。

因此，**即使完全按当前说明执行，也可能只生成规则入口，没有说明这个项目如何开发。**

建议在生成或补齐时检查以下内容，按项目实际情况写入：

| 内容 | 信息来源与要求 |
| --- | --- |
| 项目概览 | 项目用途、实际技术栈、前端／后端／全栈类型；保持简短。 |
| 目录职责 | 只列与日常开发有关的真实目录，以及页面、服务端、公共代码等边界。 |
| 常用命令 | 根据包清单、锁文件、工作区配置和已有文档核对开发、构建、检查、测试命令；不存在的命令不编造。 |
| 局部差异 | 某个包或目录有独立命令、职责或约束时，在合适层级说明。 |
| 规则入口 | 接入现有个人规则，继续按需读取。 |

这些栏目是检查维度，不是必须全部生成的固定空模板。证据不足时略去并说明，不留下空章节。命令从配置核对存在，不代表实际执行成功；初始化不需要安装依赖或运行完整业务构建。

已有文件包含等价内容时直接复用，不为统一标题而重写。已经过时的项目事实，仅在当前配置或源码能明确证实时修正；含义不明的约定不擅自覆盖。

### 3.2 覆盖缺口：前后端一体项目不一定是 monorepo

依据：[覆盖范围](../skills/setup-project-agents/SKILL.md) 第 10—14 行、[规则选择单位与布局](../skills/setup-project-agents/references/rule-selection.md) 第 5—39 行。

当前主要按“单体前端、单体 Node.js 后端、前后端 monorepo”描述，并以根和真实包作为选择单位。缺少对以下情况的明确指导：

- Next.js、Nuxt 等单个应用同时包含页面和服务端逻辑。
- 普通仓库中有前端与服务端目录，但没有声明工作区，也不属于 monorepo。
- 同一包内，只有部分目录或文件职责适用前端规则。

建议把选择单位改为：**项目根，以及确有独立职责或约束的包、目录或代码范围。** 是否创建子级 `AGENTS.md`，由内容是否需要独立生效决定。

| 项目形态 | 建议处理 |
| --- | --- |
| 单体前端 | 根入口包含项目上下文、通用规则和适用前端规则。 |
| 单体 Node.js 后端 | 根入口包含后端项目上下文和现有通用规则；不套用前端规则。 |
| 单应用全栈 | 根入口说明页面与服务端边界；前端规则的触发条件明确限定页面、组件等前端职责，必要时补充局部入口。 |
| 普通前后端分目录仓库 | 按真实目录职责组织入口，不要求先改成工作区或拆包。 |
| 前后端 monorepo | 根说明工作区与通用约定；子包承载独有信息和适用规则。 |

特别是单应用全栈，不能因为同一个包使用 React 或 Vue，就让所有服务端代码都承担组件、样式和浏览器相关规则。职责混在同一目录时，通过准确的触发条件表达，不强制调整源码结构。

“不创建空入口”应保留，但应允许有独立项目说明或命令的范围拥有入口；没有规则正文时，不必同时创建空 `.agents/rules/`。

### 3.3 确定遗漏：表单回填规则未进入选择清单

依据：

- 已存在 [表单回填规则](../skills/setup-project-agents/assets/rules/frontend/表单回填.md)。
- [前端入口模板](../skills/setup-project-agents/assets/AGENTS.frontend.md) 第 13 行已有对应入口。
- [规则选择清单](../skills/setup-project-agents/references/rule-selection.md) 的资产组合表没有对应组合。

静态交叉检查发现：13 份规则资产中，只有这一份没有被选择清单引用。

清单第 13 行已有“枚举资产并处理差异”的兜底，因此不能断言每次都会漏写；但它确实造成了维护不一致，让正常流程依赖额外判断。

建议补充 `frontend-autofill` 组合，明确适用于有浏览器自动填充样式职责的 Web 前端范围，排除纯后端及无浏览器样式职责的范围。规则正文与对应入口同步选择，保留现有个人规则内容。

### 3.4 措辞歧义：“补齐”和“模板升级”的界限不清楚

依据：[SKILL.md](../skills/setup-project-agents/SKILL.md) 第 22 行。

当前同时要求：本次补齐必须完整比较当前个人规则基线；只有明确要求时才对已接入项目执行模板升级。

例如，项目以前接入过规则，当前模板新增一条适用规则。用户这次说“查漏补缺”，这条新增规则应被补入；现有措辞却容易让执行者把它理解为另需授权的模板升级。

建议直接定义：

- 用户本次要求初始化或补齐，即比较当前适用基线，补齐其中缺失的要求。
- 不因模板文件改名、删除或重新分组，就迁移、删除项目已有规则。
- 没有新的用户请求时，不主动把模板后续变化回写项目。

这样可以去掉含义重叠的“模板升级”概念。用户明确要求迁移、清理时，再按该次请求处理，不为日常补齐增加确认环节。

### 3.5 作用范围歧义：前端“页面接口”规则用了“所有后端接口定义”

依据：[前端入口模板](../skills/setup-project-agents/assets/AGENTS.frontend.md) 第 8 行、[页面接口规则](../skills/setup-project-agents/assets/rules/frontend/页面接口.md) 第 4 行。

这份规则被选择清单归入前端范围，但入口写“新增、修改后端接口定义”，正文写“所有后端接口定义”。在全栈项目中，容易被理解为约束全部 Node.js 服务端实现。

建议将此处明确为“前端调用的后端接口契约／请求与响应定义”，保留明确类型和 JSDoc 的要求。

这是需要随本方案确认的范围澄清。如果你的原意是后端实现本身也必须遵守相同要求，应另行明确后端入口和作用范围；本轮不自行增加后端框架规范。

## 5. 优化后的执行流程草案

建议以以下流程作为新版 `SKILL.md` 的主线：

1. **确定范围。** 使用指定项目；读取覆盖目标的已有指令和相关规则，读取范围不意味着扩大修改范围。
2. **识别实际结构。** 确认项目类型、技术栈、包或目录职责、包管理器和可核对的命令。
3. **检查项目上下文。** 对照项目概览、目录职责、命令和前后端边界，识别需要新增、补齐或修正的内容。
4. **选择个人规则。** 根据规则清单逐个范围选择适用资产；仅对相关 React 范围读取 Compiler 检测说明。
5. **生成或合并。** 没有文件则建立必要入口；已有文件则保留有效内容、补缺去重，并处理链接与参数。
6. **校验并交付。** 核对事实、作用范围、规则覆盖和链接，说明变更、条件跳过项与真正待定的冲突。

合并原则继续保留：完整覆盖则复用，部分覆盖则补齐；同主题不代表相同语义；不擅自弱化适用的个人规则；不覆盖无关内容和工具维护块。

整体修改仍限于目标范围内的 `AGENTS.md`、规则文档及必要入口链接，不因为生成文档而改动业务代码、依赖或构建配置。

## 8. 原确认建议与实际决定

原方案建议以下三点，其中第 1 点未被采纳；最终实施范围见第 9 节。

3. **保留个人规则基线。** 修复清单遗漏、澄清页面接口范围、精简流程，不改弱现有个人约束，也不额外创造后端框架规范。
